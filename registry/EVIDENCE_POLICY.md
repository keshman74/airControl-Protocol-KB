# Политика доказательств и статусов

Обязательная единица оценки: **ID + устройство/product + прошивка + протокол/порт + параметры + наблюдаемый эффект**. Неизвестная прошивка остаётся unknown. Широкий Device в старом CSV — область кандидатов, а не матрица аппаратной поддержки.

| Статус | Что разрешает утверждать |
|---|---|
| CONFIRMED | Аппаратный запрос/эффект проверен в явно указанном контексте; readback, audible effect и интеграционная проверка различаются |
| DOCUMENTED | Подтверждён документацией/SCPD/исходным API-описанием; указывать official или community |
| APK-VERIFIED | Найден builder/parser/callsite приложения; не доказано исполнение устройством |
| EXPERIMENTAL | Гипотеза, реализация/наблюдение без достаточного подтверждения заявленного эффекта |
| REJECTED | Реальный отрицательный результат в данном контексте; HTTP 200 с unknown command тоже отказ |
| SUPERSEDED | Конкретный старый вывод заменён более сильным; обязательны причина и superseded_by |

Статус не кодирует всё: отдельно сохраняются тип источника, CAPTURED, IMPLEMENTED, host-tested/build-passed, endpoint-tested, write-only, число испытаний, диапазон, response vs effect. Старые строки сохранены дословно. Генератор классифицирует CAPTURED/IMPLEMENTED без отдельного результата как EXPERIMENTAL **для утверждения успешного исполнения**, сохраняя сам факт capture/implementation. Это не опровержение сетевого наблюдения.

`SOURCE-CONFIRMED`/callsite относится к коду и консервативно маршрутизируется как APK-VERIFIED; конкретный тип источника уточняется в исходном документе. UNKNOWN/PARTIAL/advertised — признаки полноты, не аппаратные статусы. Тест, сломанный из-за BusyBox grep, — invalid, не REJECTED.

Исторические CSV не обновляются задним числом. Текущие контекстные уточнения хранятся в [KB_DECISIONS.json](KB_DECISIONS.json) и страницах протокола; [каталог](audit/catalog.json) показывает оба уровня. Он не выбирает «максимальный» статус для всех устройств.

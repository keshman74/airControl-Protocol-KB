## A31, A97 and A98 are not interchangeable labels

`com.wifiaudio.model.DeviceProperty.isA98()Z` returns **false only for uppercased hardware A28 or A31**. Every other hardware string, including empty or unknown values, reaches true. This is a legacy/new-family branch, not proof of a physical A98 chip.

`com.linkplay.mrm.j.d(DeviceItem)` uses a different configurable criterion:

| Condition | Modern multiroom branch |
|---|---|
| `config.a.A2 == false` | non-null, non-empty `wmrm_version` |
| `config.a.A2 == true` | broad `DeviceProperty.isA98()` |

The deployed/runtime value of the app configuration flag was not established. Do not replace this condition with an unconditional chip-name rule.

The DEX string-pool search found no standalone A97 token, but **did find `ALLWINNER-R328`**. `com.wifiaudio.service.l.l(DeviceItem)` explicitly accepts either `AmlogicA113` or `ALLWINNER-R328` and invokes `action.j0.b.c(device,"2:0","5:0",callback)`. That method converts the two local times through its UTC formatter, then `action.s.b.j` builds `setMvRemoteSilenceUpdateTime:<start>_<end>`. These arguments concern a quiet-update window, not a universal playback capability. Smali fallback fully exposes the hardware comparisons (REA `ev_aada68a5aa94943d26a15b7f0a8cf36a22469e39ad04c92f1c2231cabdf3ef28`).

`DlgDevSettingOptions_2.t0()` also requires `config.a.N3 && hardware.equals("ALLWINNER-R328")` to expose `_5GOnly`. The UI gate is observed; it does not prove every R328 board has a working 5 GHz radio. The KB's A97↔R328 relationship comes from earlier hardware classification, not a new explicit A97 label in this APK.

## HTTP/HTTPS endpoint selection

Source: `utils.e1.g.E/F/I/J`, `action.s.a.O/y`, `DeviceProperty.withJsonConvert`.

The normal prefix is `<scheme>://<device>/httpapi.asp?command=`. `g.J` treats only case-insensitive `http` as unencrypted. The status parser normalizes `https/3.0`→`https 3.0`, `https/2.0`→`https 2.0`, `https`→`https`; missing/unrecognized status security becomes `http`. Explicit `security_version == "3.0"` overrides it to `https 3.0`.

- Normalized `http`: HTTP, implicit port 80.
- Secure status without `bHasgc4aVer`: HTTPS, implicit port 443.
- Secure status with `bHasgc4aVer`: HTTPS **4443**. The parser sets this flag from presence of the `gc4aVer` property; it is not a generic A98 rule.
- `getStatusEx`/`getDebugInfo` bootstrap helpers accept a separate secure boolean and perform the same known-device 4443 check.
- `g.I(slaveInfo,masterIP)` makes a master-targeted prefix ending `command=SlaveIP:<slaveIP>`. Its scheme test uses the supplied slave security; its 4443 lookup uses the master.

`g.G/H` chooses a plain client for HTTP, the old-certificate client for exact `https`, and the newer client for other secure variants. `EncryptedHttpsBase` initializes TLS key managers from a PKCS12 asset. Certificate material, private keys and native password-returning functions are outside the published evidence. This implementation detail does not establish that arbitrary HTTPS clients will be accepted.

Existing KB hardware mapping remains authoritative: tested A31 HTTP80, A97/A98 HTTPS443 for HTTPAPI. UPnP uses the advertised service/control URL independently. No universal HTTPS/port rule follows from the chip alone.

## Multiroom: direction and branch matter

Sources: `com.linkplay.mrm.{b,d,f,h,j,CompatibleMultiRoomManager}`. Routing status: client implementation only.

| Operation | Request target | Format / decision |
|---|---|---|
| Modern classic join | joining slave | `multiroom:JoinGroup:IP=<masterIP>:uuid=<masterUUID>` |
| Legacy-master join | joining slave | `ConnectMasterAp:...:JoinGroupMaster:eth<eth2>:wifi<apcli0>:uuid<uuid>` |
| Classic modern-master leave | leaving slave | `multiroom:LeaveGroup` |
| Classic legacy-master leave | master | `multiroom:SlaveKickout:<slaveIP>` |
| MRM4 leave | master | `multiroom:SlaveKickout:<slaveIP>` regardless of ignored isA98 return |
| Slave volume/channel/name | master | `multiroom:SlaveVolume:<slave>:<int>`, `multiroom:SlaveChannel:<slave>:<int>`, `multiroom:SlaveDeviceName:<slave>:<name>` |
| Slave alarm query/tone | master | `SlaveIP:<slaveIP>:alertget` / `SlaveIP:<slaveIP>:talksetAlarmTone:<int>` |

Classic d.b rejects a modern master + legacy slave (`A31 can not join to A98!!!`). However, the manager searches the selected group for a legacy device and can **promote it to master**. Do not document this as a blanket prohibition of mixed A31/new-family multiroom.

Legacy join builds one string:

```text
ConnectMasterAp:[ssid=<uppercase UTF-8 hex>:]ch=<channel>:auth=<auth>:encry=<encryption>:pwd=<uppercase returned pwd>:chext=0:JoinGroupMaster:eth<eth2>:wifi<apcli0>:uuid<uuid>
```

Square brackets indicate an optional field, not wire bytes. `ssid=` is omitted when `softap_enable == "0"`. Auth/encryption is WPA2PSK/AES when `secureMode == "1"` **or** returned password is nonempty; otherwise OPEN/NONE. The password is uppercased as received, not proven to be plaintext-hex-encoded here. Smali resolves a decompiler uninitialized-boolean artifact in this condition. Classic getNetwork failure falls back to empty credentials/open network; MRM4 reports failure instead. This is observed app behavior, not a recommended provisioning strategy.

MRM4 join class h uses master.isA98 directly, without the classic slave-class rejection. The feature gate choosing classic versus MRM4 was not fully traced. Classic completion also waits for matching SLAVE_ADD/slave-list UUID or registry state; an HTTP success alone does not establish completed grouping.

## EQ and MCU control

Two distinct surfaces must remain separate:

1. HTTP EQ: B.f/g/h/f0/g0 emit `getEqualizer`, `EQEnable`/`EQDisable`, `EQGet`, `EQSet:Bass:<int>`, `EQSet:Treble:<int>`. E additionally emits `EQOn`, `EQOff`, `EQGetBand`, `EQGetList`, `EQLoad:<string>`, `EQSave:<string>`, `EQSetBand:<string>`, `EQGetLV2Band:<string>`, `EQSetLV2Band:<string>`, `EQv2GetList:<string>`, `EQv2Load:<string>`, `EQv2Rename:<string>`, `EQv2Delete:<string>`, `EQChangeFX:<string>`, `EQGetFXList`, `EQGetSourceModes`. Strings are forwarded; band JSON/value semantics are not invented from method names.
2. MCU passthrough builders `com.wifiaudio.view.pagesdevcenter.equalizersettings.f.a`:

| Method | Literal / format |
|---|---|
| a | `MCU+EQ++GET` (double plus; no appended ampersand) |
| b/e | `MCU+PAS+EQSet:bass:%02d&` / `MCU+PAS+EQSet:treble:%02d&` |
| c/f | `MCU+PAS+EQGet&` / `MCU+PAS+EQG&` |
| d | `MCU+PAS+EQSet:mode:%02d&` |
| g/h | `MCU+PAS+HDMIGet&` / `MCU+PAS+HDMISet:%03d&` |

These widths are minimum decimal formatting widths, not validated numeric ranges. Response parsers recognize `MCU+PAS+EQ:bass:`, `treble:`, `mode:`, `enable:` and `MCU+PAS+HDM+`; parse failure commonly returns zero, so zero is not proof of a successful read. `MCUCmdThread.t` sends EQGet; g parses bass/treble callbacks.

`MCUDispatchThread.r` packs **20 header bytes + payload bytes**: little-endian uint32 magic 538482200 (`0x20189618`, wire `18 96 18 20`), payload byte count, third uint32 passed as zero, then eight zero bytes. Payload follows at offset 20. `utils.i.e` explicitly writes little-endian bytes; this sender does not compute a payload checksum. The socket port is supplied to the constructor, not fixed in the frame builder. DeviceProperty parses `uart_pass_port` and `communication_port` separately. Do not infer that port 8819 and UART 8899 share this framing without tracing the actual caller/device.

`BassTrebleActivity` contains additional project-specific `MCU+PAS+B%02d&`, `T%02d&`, `S%02d&`, `V%02d&`, and conditional M/F variants. These are not generic A31/A97/A98 commands; project gates and actual hardware applicability remain unresolved. They are recorded here to prevent importing arbitrary OEM UI code as universal chip functionality.

- A97 getPresetInfo HTTP-200/unknown-command result remains unchanged. Preserve existing GetKeyMapping + MCUKeyShortClick and paced RenderingControl volume implementation.

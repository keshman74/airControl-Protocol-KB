# A33 preset HTTP API — hardware test (2026-10-10)

Device: A33 airCloud at 192.168.0.31, HTTP ACS2 port 8000. User performed tests locally on Mac.

## Observed results
- `GET /?Instruct=getPresetListInfo` returned JSON with `Presets` array containing **12** entries, numbered 1–12.
- Verified response fields: `PresetNumber`, `PresetName`, `Volume`, `EqData`, `StreamMediaName`, `InputMode`, `LoopMode`, `MusicData`, `Logo`, `Ip`. All tested slots used Qobuz. `MusicData` can contain authentication tokens and token-bearing URLs: **never log, commit, or expose raw response without redaction**.
- `choicePreset:1`: first trial returned `Not`; second trial returned `OK`. User confirmed slot 1 switched and started playing.
- `choicePreset:2`: returned `Not` in trials, but user confirmed it **switched to slot 2 without starting playback**.
- After `choicePreset:2`, waiting 2 seconds and sending `setPlayerCmd:resume` started playback successfully.
- Thus `Not` is **not a reliable indicator of failed preset selection** on this tested A33; do not blindly retry.
- Preset selection and auto-play are distinct; slot 1 played automatically, slot 2 needed resume.

## Gateway implementation recommendation (not yet firmware/hardware verified)
- Map `PRESET_1` through `PRESET_12` on **A33 only** to ACS2 HTTP `choicePreset:<N>`.
- Nonblocking schedule: after selection, allow up to ~2000 ms for state transition, then query player state; issue `setPlayerCmd:resume` **only if paused/stopped and selection still current**. If state unavailable, the tested fallback is choice → 2s → resume, but mark as fallback, not proven necessary for every slot.
- Newer KNX preset command cancels any pending resume for the older selection. Never retry choice automatically on `Not`.
- Keep A31/A97/A98 MCU preset mechanism separate and unchanged.
- Avoid blocking `delay()` in KNX event path.

Evidence: user-supplied terminal outputs and explicit playback observations, 2026-10-10. No Qobuz secrets copied here.

# airALARM — передача контекста разработки

**Дата составления:** 22 октября 2026 г.  
**Статус:** предварительная реконструкция по доступному разговору и найденным техническим материалам. Это **не** полный экспорт старого чата airALARM.

## Цель
Перенести проверяемые сведения о проекте airALARM в новый чат ChatGPT и затем в GitHub, чтобы продолжить разработку через Codex без потери решений.

## API тревог — восстановленные договорённости
- Интервал опроса: 120 секунд.
- После HTTP 429 без `Retry-After`: пауза 120 секунд; учитывать `Retry-After`, если присутствует.
- Порог устаревания данных: 300 секунд.
- При потере связи сохранять последнее достоверное состояние; **не объявлять отбой тревоги автоматически**.
- Отклонять некорректный `activeAlerts`.
- Хранение состояния после перезагрузки не подтверждено.
- В предыдущем анализе отмечалось отсутствие проверки TLS-сертификата; перепроверить по исходникам.

## Платформа и интеграция аудио
- Проект ESP32 airALARM; упоминаемый локальный каталог: `/Users/lab/AI/airALARM`.
- В техническом отчёте по A31 фигурирует адрес ESP32 `192.168.0.42:8082` для раздачи MP3 и A31 `192.168.0.35` (Rakoit 4.6.415156). Адреса — параметры конкретного теста, не универсальные настройки.
- 16 октября команда `playPromptUrl` с параметром громкости `10` вернула HTTP 200/OK; сообщение звучало тише, интернет-радио возобновилось с прежней громкостью. Длительная безопасность и стабильность метода **не подтверждены**.
- В исследовании A33 встречались ответы HTTP 400 на `downloadPromptSound`; это не подтверждение поддержки функции.

## Ограничения OTA
Для 0.1.30 WiFi и 0.1.31 указан OTA-раздел 1 310 720 байт и требуемый резерв 32 768 байт. Перед новой сборкой перепроверить реальную таблицу разделов и размер бинарника 1.4.

## Правила для Codex
- Не менять контрольную рабочую сборку и опубликованные OTA-артефакты без явного решения владельца.
- Не объявлять функцию проверенной только по успешной компиляции.
- При проблемах API не трактовать сетевой сбой как окончание тревоги.
- Перед релизом проверять размер прошивки, OTA-раздел, обработку ошибок, воспроизведение аудио и восстановление сети.
- Фиксировать изменения в `CHANGELOG.md` и результаты аппаратных тестов отдельно.
